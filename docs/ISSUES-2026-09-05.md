## Implemented fixes

### A01 — Reject an unknown product before writing anything

Location: `backend-fastapi/app/main.py`, `add_session_item`.

Before: posting a nonexistent `product_id` returned 200 under the SQLite test
configuration and persisted an orphan. Reading or completing that session could
then dereference `item.product == None`. With foreign keys enforced, the insert
would instead raise an unhandled database error.

Implementation: after session authorization, replay lookup, and active-state
validation, look up the product and return 404 `Product not found` before flushing
an item or writing its operation/acknowledgement. Existing response fields remain.

Acceptance: no item, SessionOp, or AppliedOp is written for an unknown product;
subsequent session reads still succeed. Cross-user authorization is still checked
before any acknowledgement is returned.

### A02 — Preserve enriched data and stable item identity

Locations: `add_session_item`, `update_session_item`, `get_session_items`, and
`complete_session` in `backend-fastapi/app/main.py`.

Before: writes built and stored an enriched DTO but returned the ORM object, so
the first response had null product/distributor names while its idempotent replay
contained names. Snapshot and completion DTO construction omitted `item_uuid`.

Implementation: return the already-built DTO from successful writes; include the
existing UUID field in snapshots and completion output. No fields were removed
or renamed. Legacy rows with null UUIDs remain compatible; no backfill is claimed.

Acceptance: first write and exact retry return identical data; reads and grouped
completion preserve the latest quantity, version, names, and the original UUID.

### A03 — Acknowledge previously committed operations after completion

Location: `backend-fastapi/app/main.py`, `add_session_item`.

Before: an add committed, its response was lost, another device completed the
session, and the retry returned 400 before inspecting the idempotency ledger.

Implementation: keep authorization first, then return a saved acknowledgement
before checking whether a **new** write is allowed. No new mutation is performed
by replay. New keys still receive 400 for inactive sessions.

Acceptance: replay returns the original DTO with exactly one operation in the
ledger and no quantity increment; another user still receives 404.

## Remaining implementation tickets

### A04 — Persist and reuse operation identity on Android

Evidence: `network/DTOs.kt` has no `idempotency_key` in `AddItemRequest` or
`UpdateItemRequest`. Both `SessionRepository` and `SyncService` send these DTOs.
The server can commit an add before a response is lost; the queued retry then
adds the same quantity again.

Implementation:

1. Add a durable operation UUID to the Android outbox and additive nullable
   `idempotency_key` fields to request DTOs. Preserve a key across process restarts.
2. Persist the outbox entry in the same Room transaction as the optimistic edit,
   before the first network call. Send the same key initially and on every retry.
3. Acknowledge/remove the outbox entry only after applying the server response.
   Backfill unique identities for older queued rows during a Room migration.
4. Coordinate with A10: sequential idempotence alone does not serialize two
   simultaneous requests carrying the same key.

Acceptance: simulate server commit followed by socket disconnect, restart the
app, replay, and assert quantity increases once. Exercise both immediate writes
and background replay; verify key equality across attempts.

### A05 — Recover retryable and interrupted outbox work

Evidence: `PendingOperationRepository.markAsFailed` computes a backoff time but
calls the DAO with the default status `FAILED`. `getReadyForSync` selects only
`PENDING`. `processOperation` sets `IN_PROGRESS`, with no stale-claim recovery.

Implementation: schedule retryable errors as `PENDING` with `scheduledFor`; retain
permanent failures in a user-visible state. Claim an entry atomically and recover
expired `IN_PROGRESS` claims after worker/process termination. Use a shared worker
lease or database claim to prevent multiple SyncService instances replaying it.
Implement after A04 so recovery is safe after an ambiguous network outcome.

Acceptance: a transient 503 retries after backoff; a killed worker resumes after
lease expiry; two workers cannot claim the same entry; a permanent rejection
remains visible and is not silently deleted.

### A06 — Reconcile server snapshots with optimistic edits

Evidence: `SessionRepository` queues only IOException failures and only logs
409/5xx responses. `WorkspaceSessionResolver.pullItems` deletes all cached items
in a session before inserting the server snapshot, without consulting the outbox.

Implementation: use A04's durable outbox for every local mutation; retain 5xx and
ambiguous failures for retry. Keep a server baseline and apply pending operations
over it in one transaction during refresh. For 409, surface/reconcile a conflict
rather than silently dropping the user's edit. Serialize refresh and edits for
the same session. Do not discard rows merely because catalog download is late.

Acceptance: edit offline, refresh while operations remain pending, and verify
the user's intended quantity stays visible and eventually converges. Repeat
with 503, 409, a missing local catalog product, and a refresh racing a new edit.

### A07 — Isolate account data and replay authority

Evidence: `SessionEntity` stores teamId but no personal owner id; a personal
session lookup uses only `teamId IS NULL`. Logout clears tokens/workspace but
does not partition cached sessions. Pending entries have nullable `userId`, but
normal session callers omit it and ready-for-sync queries do not filter by user.
`InventoryItemEntity` is intentionally one device-local list with no owner/team.

Implementation: associate authenticated identity with local sessions and every
outbox entry; select/cache/replay strictly for the current identity and workspace.
Cancel or invalidate in-flight work on account changes. Quarantine legacy
unowned operations until their owner can be established; do not replay them
under whichever account logs in next. Preserve each account's unsynced work.
If inventory is per store/account, migrate it to the chosen workspace scope too.

Acceptance: user A edits offline and logs out; user B logs in while disconnected.
B cannot see A's personal list or submit A's operations. A can return and resume.
Also test two users who share a team and token expiry followed by a different login.

Decision requested: should inventory remain shared on the device or belong to a
specific account/store? Personal-session and outbox isolation is still required.

### A08 — Upload sessions first created offline

Evidence: `SessionDao.getOrCreateActiveSession` creates a negative local id.
SessionRepository returns before networking/queueing for that id. Resolving a
server session later deactivates the local fallback without migrating its items.

Implementation: introduce a stable local session UUID and a durable create-session
operation. On reconnect, create/resolve the authorized destination, persist the
local-to-server mapping, then remap and replay dependent item operations in order.
Keep the local list available until promotion has been acknowledged. Make session
creation idempotent through an additive backend contract.

Acceptance: first launch offline, add several items, restart, reconnect, and
verify all items reach the intended workspace once without an abandoned list.

### A09 — Make offline completion a durable action

Evidence: `SessionRepository.completeSessionWriteThrough` closes locally before
the request; an IOException is logged without a completion operation. The server
remains active and the resolver later restores it.

Implementation: queue a completion intent behind the session's item operations;
display "waiting to sync" until the server acknowledges it. Persist the exported
snapshot so PDF content corresponds to the intended completion. Use an idempotent
completion acknowledgement and explicitly handle other users' intervening edits.
Avoid clearing data before successful export and durable intent persistence.

Acceptance: complete and export offline, kill/restart, reconnect, and verify
exactly one completion with consistent items/PDF and no accidental reopening.

### A10 — Serialize backend mutations per session

Evidence: `sync_ops.next_seq` uses `max(seq) + 1`; the schema has a non-unique
index on `(session_id, seq)`. Quantity and version checks use read-modify-write
without a row lock or atomic conditional update. The AppliedOp lookup also
precedes insertion without a concurrency claim. Multiple server workers can
race even when sequential tests pass.

Implementation: acquire a per-session database lock before reading mutable state
or checking the idempotency ledger, consistently for add/update/delete/clear and
completion. Use atomic version predicates for optimistic writes and a unique
sequence constraint as a final guard. Audit existing duplicate sequences before
adding a constraint; retry transaction conflicts without changing operation keys.
Define SQLite write serialization separately because SELECT FOR UPDATE does not
provide the PostgreSQL behavior there.

Acceptance: use separate PostgreSQL connections with synchronization barriers:
simultaneous increments preserve the sum; competing absolute updates yield one
409; duplicate keys cause one mutation; op sequences are unique and ordered.
The current passing SQLite suite does not prove these properties.

### A11 — Define the completed-list mutation contract

Evidence: add checks `is_active`; update, delete, and clear authorize access but
do not check it. Completed PDF data and saved list contents can then diverge.

Decision requested: completed lists immutable, or editable after completion?

Implementation if immutable: enforce an active-session guard for new mutations
while retaining acknowledgement replay and historical reads/exports. Give the
client an explicit actionable error and offer a new list/correction workflow.
If editable: version the completed snapshot and regenerate/export the revised
version so an old PDF cannot silently describe a different list.

Acceptance: exercise every mutation against an active and completed session,
including retries; verify UI handling and repeat PDF exports match the policy.

### A12 — Validate session quantities at the API boundary

Evidence: create/update schemas accept unrestricted integer quantities. An add
with a negative quantity can reduce an existing line; new negative/zero lines
can appear in totals. Android normally deletes through DELETE for quantity <= 0.

Implementation: require positive quantities for additions, nonnegative versions,
and bounds compatible with database integers. Confirm whether PUT quantity=0 is
invalid or means deletion, then enforce that rule consistently with the Android
client. Bound idempotency keys to the ledger column size. Validate in request
models without restricting DTOs needed to read legacy data; plan cleanup of old
invalid rows separately rather than deleting them automatically.

Acceptance: zero/negative/overflow quantities cannot corrupt totals or create
ledger entries; invalid updates leave quantity and version unchanged; supported
mobile requests continue to work.
